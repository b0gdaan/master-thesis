# Контракт воспроизводимости для нового проекта

Это требования к будущей реализации. Приведённые команды и структура являются образцом интерфейса; в старом проекте они не реализованы в таком виде.

## Структура

```text
project/
  README.md
  requirements.lock          # либо другой проверенный способ фиксации окружения
  configs/                   # схема, smoke-конфигурация, полный эксперимент
  src/                       # данные, преобразования, методы, оценка, экспорт
  tests/                     # unit, integration, reproducibility
  data/raw/                  # неизменяемый разрешённый снимок
  data/processed/            # результат кода, связанный с raw-хешем
  runs/<run_id>/             # manifest, логи, predictions, metrics, модели
  notebooks/                 # объяснение и диагностика
  reports/                   # таблицы, графики, реестр утверждений
  thesis/                    # текст и библиография
  presentation/              # слайды и речь
  docs/                      # протокол, решения, восстановление, handoff
```

Проект должен работать после переноса папки. Большие или закрытые данные могут храниться отдельно, но способ их получения и контрольные суммы должны быть документированы.

## Команды и этапы

Предлагаемый CLI: `python -m research <command>`.

| Команда | Контракт |
|---|---|
| `doctor` | Проверить runtime, зависимости, конфигурацию, пути и ресурсы |
| `smoke` | Маленький полный эксперимент на фиксированных данных без сети |
| `run --config ...` | Все обязательные этапы, включая абляцию и дополнительные проверки |
| `resume --run-id ...` | Проверить готовые выходы и продолжить незавершённые этапы |
| `verify --run-id ...` | Проверить полноту, уникальность, хеши, метрики и происхождение |
| `report --run-id ...` | Собрать таблицы, рисунки и текстовые вставки одного запуска |
| `release --run-id ...` | Выпустить согласованные материалы после обязательных проверок |

Граф этапов: данные → проверка → преобразования → разбиения → обучение → прогнозы → оценка → диагностика/абляция → отчёт → релиз. Точные зависимости описываются явно. Запуск без обязательного этапа имеет статус `incomplete` и не выдаётся за полный.

## Manifest запуска

Минимальные поля:

```yaml
schema_version: 1
run_id: "<unique id>"
status: pending
created_at_utc: "<timestamp>"
code_commit: "<commit>"
working_tree_dirty: false
source_bundle_sha256: "<hash if uncommitted changes are used>"
config_sha256: "<hash>"
data_sha256: "<hash>"
split_sha256: "<hash>"
environment_sha256: "<hash>"
seed: 42
device: "<cpu/gpu and relevant details>"
stages: {}
artifacts: []
verification: {}
```

Каждый этап хранит статус `pending/running/succeeded/failed/interrupted`, попытку, время, входные хеши, выходные хеши и текст ошибки. `succeeded` допустим только после проверки завершённых выходов. Смена кода, данных, окружения или конфигурации требует проверки инвалидируемых этапов.

Сохранённый прогноз содержит идентификатор объекта, разбиение/fold, модель, target, prediction, run_id. Для временной задачи дополнительно нужны момент выпуска, момент целевого события, граница доступных обучающих меток и версия модели. Уникальный ключ предотвращает повторные строки.

## Восстановление

1. Проверить manifest и наличие входов с ожидаемыми хешами.
2. Найти завершённые этапы, проверить целостность и происхождение их выходов.
3. Повторить прерванные дешёвые этапы; долгие восстановить из проверенного checkpoint.
4. Состояние долгого обучения должно включать необходимые параметры модели, оптимизатора и генераторов случайности.
5. Выполнить оставшиеся зависимые этапы и проверить полноту результата.

Запись: временный файл → проверка → атомарное переименование на том же файловом томе. Параллельные задачи пишут отдельные файлы. Финальное объединение имеет фиксированную сортировку и проверку ключей. Файл от предыдущей версии нельзя молча принять за результат текущего запуска.

## Матрица содержательных тестов

| Проверка | Какую ошибку должна обнаружить |
|---|---|
| Схема, типы, диапазоны, уникальность | Повреждённые входы и неверные единицы |
| Ручной маленький пример через функции проекта | Ошибочную формулу, сдвиг, преобразование или метрику |
| Независимость train/test по объектам или группам | Попадание одного объекта в запрещённые части |
| Доступность меток к моменту решения | Обучение на ещё неизвестном результате |
| Изменение будущих данных | Изменение прошлых признаков или прогнозов из-за утечки |
| Fit preprocessing только на train | Подглядывание в отложенное распределение |
| Корректные вневыборочные входы второго слоя | Обучение второго слоя на подогнанных прогнозах первого |
| Одинаковое покрытие сравнения | Исключение трудных объектов только у части моделей |
| Пересчёт метрик из сохранённых прогнозов | Устаревшую или неправильно агрегированную таблицу |
| Два одинаковых запуска | Дубликаты, недетерминированность сверх допуска |
| Изменение входа при прежнем размере | Ошибочное повторное использование кэша |
| Прерывание и resume | Потерю состояния или повторное выполнение с другим результатом |
| Искусственная ошибка обязательного этапа | Ложный успешный exit code или выпуск неполного отчёта |
| JUnit с failed/skipped/error | Ложную подпись «все тесты пройдены» |
| Чистая установка и smoke без сети | Зависимость от локальных пакетов и старых файлов |
| Эталонный прогноз и экспорт | Расхождение признаков, весов или порогов демонстрации |

Тест изменения будущего сравнивает только величины, которые должны быть доступны до выбранной границы. Будущие истинные метки могут закономерно измениться. Для горизонта больше одного шага нужно проверять время доступности каждой обучающей метки, а не только порядок строк.

Тесты вызывают реальные функции проекта. Ожидаемые ответы на маленьких примерах вычисляются независимо. Утверждение «наша модель обязана победить» не является инвариантом корректной программы.

## Статистика и подтверждение результата

Протокол фиксирует основной вопрос, метрику, минимально полезный эффект, разбиение, бюджет настройки и способ оценки неопределённости до итогового теста. Метод оценки зависит от структуры данных: временной, групповой, пространственной или независимой.

При зависимых наблюдениях требуется обоснованный способ учитывать зависимость, например подходящий блочный bootstrap или оценка стандартных ошибок. Множественные сравнения и выбор лучшей конфигурации учитываются в выводах. Непроверенные предпосылки обозначаются явно.

Абляция использует одинаковые условия и общую выборку сравнения. Если меняется определение цели, отдельно отмечается, переобучался ли метод. Практическая польза оценивается отдельным экспериментом с ограничениями реального применения.

## Связь с текстом и выпуск

Реестр `CLAIMS` хранит: `claim_id`, раздел, формулировку, `run_id`, файл, фильтр, метрику, интервал и ограничение. Таблицы и рисунки генерируются из того же запуска. Ручное округление документируется.

Для публичной и печатной версий используются разные явные имена. Релиз хранит версии исходников, manifest, отчёт тестов и контрольные суммы. В демонстрации обозначаются дата данных, версия модели и режим: работающая модель, сохранённый снимок или сценарий.

Готовность подтверждается выполненными действиями: чистая установка, smoke, основные эксперименты, тест восстановления, пересчёт метрик и визуальная проверка итоговых материалов. В журнале указываются фактическое окружение, время, допуски и невыполненные проверки. Число успешных тестов само по себе не доказывает научный вывод.

## Передача следующему исполнителю

`HANDOFF.md` должен содержать: текущий вопрос, актуальный commit/run_id, путь к данным и способ восстановления, команды, завершённые этапы, текущую проблему, ближайший шаг, известные ограничения и ссылки на решения. Обновлять после содержательного этапа.
